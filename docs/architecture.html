Engineering architecture

Work Agent

An autonomous work-orchestration system for Jira, Slack, and GitHub — independent agent pipelines, coordinated by one orchestrator, gated by a single human-approval queue wherever judgment matters more than policy.

Daily engineering work is scattered across three systems that don't talk to each other: tickets in Jira, conversations in Slack, review activity on GitHub. Building a picture of what actually needs attention today means checking all three by hand, every time.

Work Agent does that checking continuously, decides what's genuinely worth attention versus noise, and — for the narrow class of work that's safe and verifiable — does it. Everything else lands in one queue with a plain-English reason and a recommendation, and waits for a decision.

How it fits together

Two ways in, one pipeline, one gate before anything consequential happens.

The pipelines

Seven real agents, split by how they run: four are always automatic; three are real and tested but only run when you ask directly, in a live session — nothing schedules them today.

Runs automatically — every trigger

Observation

Collects your open Jira tickets, GitHub PRs, and relevant Slack messages; links a PR or message to the ticket it's about; classifies each into urgency and category; writes the daily briefing and diffs it against last run.

Slack Intelligence

Classifies every message into one of 8 categories — urgent, task assignment, decision needed, action needed, response needed, important context, informational, irrelevant. Only the first six get remembered; the rest is discarded.

Work Log · Daily · Weekly Summary

Reporting, built only from the real audit trail and your own logged hours — see Time Tracking below.

Scheduler

Restart-safe, persisted job runner. Re-triggers the three agents above on a timer with zero input — the one piece of genuinely unattended automation in the system.

Real and tested — but only when you ask directly, in a live session

Task Intelligence

For a ticket you point it at: pulls the full context — description, comments — and runs the same autonomy policy Engineering Execution uses, to decide: clear enough to hand off, or too ambiguous without you.

Engineering Execution

For a ticket that clears policy: isolated git worktree, a coding agent implements it, tests/lint/typecheck/build are independently re-run — never just the implementer's own word — then, optionally, a real screenshot and short GIF of the change, then branch, commit, push, draft PR. Already used to open a real pull request on a real repository, end to end.

PR Monitoring

Watches review feedback on an open PR you point it at. A typo, a rename, a missing test, a docs fix gets applied directly onto the same branch. Architecture, security, scope, or product feedback gets escalated, never guessed at.

Inside Engineering Execution

The one pipeline that touches real code. Here is exactly what it checks, at every step, before anything reaches a repository.

A ticket only reaches this pipeline if it passes every one of these

Issue type, priority & status

Only a task or bug, only low/medium priority — never high/urgent — and only if Jira's own status is to do.

Enough description to act on

At least 80 characters of real description. Anything shorter reads as "not enough context to implement safely" and is left alone.

No explicit hold instruction

The full text — description and every comment — is checked for phrases like "don't start," "keep on hold," "paused for now." Any match disqualifies it immediately.

Nothing sensitive

Auth, permissions, security, payments, billing, credentials, PII — excluded regardless of how small the change looks, because the blast radius isn't visible from the diff alone.

Before a commit is ever made, the safety gate checks

Every check actually passes

Tests, lint, typecheck, and build are re-run independently inside the worktree — the implementer's own claim of success is never trusted on its own.

The diff is scoped

No more than 15 changed files, and never empty. Too large a change or a no-op both stop here rather than proceeding.

No forbidden paths touched

CI workflow files, .env*, database migrations, and lockfiles can never be part of an autonomous change, no matter what else passed.

Once the gate passes, one optional extra: showing the change

Opt-out, not opt-in

Any repo Engineering Execution already works in gets a best-effort attempt automatically — its own package.json "dev" script and port 3000, auto-detected, no config needed. A repo can disable this explicitly; a config entry can override the command, port, or add a documented test-login for an app that needs signing in.

A real headless browser

The app's own dev server is started inside the isolated worktree; a headless Chromium (Playwright) navigates to the changed page, optionally clicks or fills something, and screenshots it — genuinely rendered, not simulated.

Never blocks the PR

A dev server that never comes up, or a selector that doesn't match, is logged and skipped — the PR still opens exactly as it would without this step. A screenshot is evidence, never a gate.

Work logging & time tracking

This is the end-to-end version: real hours, written to real Jira, on real tickets — not a local-only simulation.

Every pipeline above writes real, timestamped events as it works — a ticket picked up, a PR opened, a review cycle. That trail is Work Log, and it's automatic. But no part of this system watches a clock, so it will never guess at how long anything took — a guess is a fabrication, and this system doesn't fabricate.

Instead, two real sources of duration feed one Jira writer, through two different levels of trust:

Automatic — gated

When Engineering Execution finishes a ticket, it measures the real elapsed wall-clock time from picking up the task to opening the draft PR — never an estimate. That duration waits in the Approval Queue; nothing is written to Jira until you approve it.

+
Ad hoc — already approved

You just ask, in chat: "log 30 minutes on PROJ-56 for last Friday." Asking directly counts as your approval, so this writes to Jira immediately — including backdating to a specific day.

Backdating works the same way either path is triggered: a specific date sets Jira's own started field on the worklog, so "log this for last Friday" actually lands on last Friday — not on whatever day the request happened to be made.

$ work-agent log-time --minutes 90 --ticket PROJ-123 --date 2026-09-11 --note "short description of the work" --jira

If nothing was logged, the report says exactly that — "no hours logged this week" — instead of estimating one. The number on your timesheet is always a number you put there, and a real Jira write only ever happens after either your explicit approval or your own direct request — never on its own.

Where the time actually goes

Reasoned estimates based on typical usage — not measured telemetry. See the caveat below.

ActivityWithout Work AgentWith Work Agent
Morning check-in across Jira, Slack, GitHub ~15–20 min of tab-switching and re-deriving context One dashboard glance, ~2 min
Triaging Slack for what actually needs a reply Scanning every channel and DM manually Noise pre-filtered; only the six signal categories surface
Picking up a small, well-scoped ticket ~30–45 min: read ticket, branch, boilerplate, PR description A go/no-go decision; implementation and draft PR happen unattended
Tracking what's pending across three systems Mental notes, easy to lose between sessions One durable approval queue, persists across every session
Preparing the weekly timesheet Reconstructing what you did from memory at the end of the week A running log of real activity plus your own logged hours, ready to submit

These are reasoned estimates from typical usage patterns, not measured telemetry — the system deliberately does not track how long anything takes on its own, so it can never fabricate a saved-hours number either.

Where this goes next

Ideas, not commitments — roughly in order of how much they'd unlock.

→
Task time estimation
When a new ticket is picked up, estimate effort from the whole surrounding context — related tickets, prior work in the same module, comment history — not just that ticket's own text in isolation. Closer to how an experienced engineer sizes work than a template guess.
→
Live Slack on the scheduler
A scoped, read-only Slack token would let the scheduler classify Slack unattended the same way it already does Jira and GitHub — closing the one remaining manual step.
→
PR Monitoring on a timer
Already built, not yet wired to the scheduler. A periodic check-and-escalate job is straightforward to add; the auto-fix step still needs a live session, same as Engineering Execution.
→
Approval-gated Jira edits
Propose a title, description, or estimate change with a clear before/after, applied only after explicit approval — the same approve-then-act pattern the Jira Worklog Writer already uses for time logging.
→
Policy that learns from your decisions
If you consistently approve one shape of suggestion and reject another, the autonomy policy's thresholds could tighten or loosen accordingly instead of staying fixed.
→
A second project, for free
The system was built project-agnostic from day one — repo and project mapping is config, not code. Onboarding another real project is a config change, not new code.

Where this stands today: sharing & deployment

Not a hosted service yet — here's exactly what that means for anyone else on the team.

Everything described above runs today as one person's tool on one machine. It isn't deployed anywhere, there's no shared server, and there's no such thing yet as a teammate "joining" your running instance — the architecture simply doesn't have a multi-user layer.

Bringing someone else in means giving them the codebase so they can run a second, fully independent instance — their own copy, their own credentials, their own local database. Nothing between the two instances is shared or synced.

AspectCurrent status
HostingRuns locally on one machine — nothing deployed to a server, cloud, or shared host
Multi-user accessNot built — no shared login, no central instance for a teammate to connect to

Slack access (optional)Each person's own token, only if they want Slack read automatically

Net resultEvery teammate ends up running a separate, independent instance — not joining this one

What you need to use it

Starting point: the code is already on your machine, and Postgres is running (see Sharing status above for that part). Here's everything else, and what each piece actually unlocks.

You needRequired?What it unlocks
A Jira API token, email, and base URL Required Reads your real tickets, and is the same credential the time-logging feature uses to write real worklogs back to Jira. One token covers both.
GitHub authenticated (gh auth login) Required for Engineering Execution Lets it read your pull requests and open draft PRs. Observation and time logging both work fully without this.
A local clone of the target repo, mapped in work-agent.config.json Required for Engineering Execution An unmapped project always means "stop and file an approval," never a guess — so this only matters once you want autonomous code changes, not before.
A Slack user OAuth token Optional Only needed if you want the scheduler reading Slack unattended. Asking me directly in a live chat session already has real Slack access without it.
Anything extra for time logging specifically Nothing It reuses the Jira token above — there's no separate credential to set up for it.
npx playwright install chromium (one time) Optional Only needed for Engineering Execution's screenshot/GIF step. It's attempted automatically for any repo it can boot — nothing else about the pipeline depends on this.

Every credential here is per-person and lives only in your own .env file on your own machine — never shared, never checked into the repo, never visible to a teammate running their own instance.
